# Flutter Assignment

주어진 Figma 디자인과 요구사항을 기반으로 관심 종목, 종목 검색 기능을 구현했습니다.

## 실행 방법

### 개발 환경

- Flutter: `3.47.3`
- Dart: `3.13.3`
- Channel: `stable`

### 실행

```bash
flutter pub get

flutter run
```

### 테스트 환경

다음 환경에서 UI 및 주요 기능을 확인했습니다.

- iOS Simulator
  - iPhone 17 Pro
  - iPhone 17e
  - iPhone 13 mini

- Android Emulator
  - Pixel 7
  - Pixel 10

### 폰트

기존 프로젝트에 등록되어 있던 `NotoSansKR` 폰트를 그대로 사용했습니다.

별도의 폰트 추가나 변경은 하지 않았으며, 프로젝트에서 제공하는 폰트 설정을 활용했습니다.

## 구현 범위

### 관심 화면

필수 요구사항을 구현했습니다.

- 관심 종목 목록 표시
  - 종목명
  - 종목코드 · 시장
  - 현재가
  - 전일 대비 등락액 / 등락률

- 상승 / 하락 / 보합 상태에 따른 색상 처리
- 상단 새로고침 버튼을 통한 시세 재조회
- 하단 탭을 통한 관심 / 검색 화면 이동
- 시세 조회 전 Skeleton UI 표시
- 관심 종목이 없는 경우 Empty State 표시
- 관심 종목 정렬
  - 현재가순
  - 등락률순
  - 가나다순

- 정렬 기준을 Bottom Sheet에서 선택
- 현재 선택된 정렬 기준을 Header Chip에 표시
- Pull to refresh

### 검색 화면

필수 요구사항을 구현했습니다.

- 종목 검색
- 검색어 입력 및 초기화
- 검색어에 대한 입력 디바운스 처리
- 검색어와 일치하는 종목명 Highlight
- 관심 종목 등록 / 해제
- 관심 종목 등록 / 해제 시 토스트 표시
- 검색 결과에서 종목 상세 화면으로 이동
- 검색 전 Initial State 표시
- 검색 결과가 없는 경우 Empty State 표시
- 검색어 초기화 시 Initial State로 복귀

### 종목 상세 화면

과제를 부여받기 전, 중요한 일정이 이미 있어서 종목 상세 화면은 구현하지 못했습니다.

따라서 다음 항목은 미구현 상태입니다.

- 현재가 및 전일 대비 정보
- 기간별 차트
- 캔들 차트
- 시세 요약 정보
- 일별 시세 테이블

다만 종목 상세 화면에 필요한 **일별 시세 HTML API의 응답 파싱 및 데이터 모델링까지는 구현**했습니다.

향후에는 다음과 같은 방식으로 종목 상세 화면을 구현할 예정입니다.

#### 1. 기간별 필요한 페이지 수 정의

기간별 필요한 거래일 수를 기준으로 필요한 페이지 수를 정의합니다.

```text
1개월 → 2페이지
3개월 → 6페이지
6개월 → 12페이지
1년   → 25페이지
```

#### 2. 페이지 단위 캐싱

이미 조회한 페이지를 다시 요청하지 않도록 Repository에서 페이지별 데이터를 `Map` 형태로 캐싱합니다.

```dart
final Map<int, DailyPricePage> _pageCache = {};
```

`Map`의 key는 페이지 번호이며, value에는 해당 페이지의 일별 시세 데이터와 `lastPage` 정보가 포함됩니다.

```text
_pageCache
├── 1 → DailyPricePage
├── 2 → DailyPricePage
├── 3 → DailyPricePage
└── ...
```

페이지를 조회하기 전에 캐시를 확인하고, 이미 존재하는 페이지는 재사용하며 캐시에 없는 페이지만 API를 호출합니다.

#### 3. 필요한 페이지만 추가 조회

기간 탭이 변경되면 해당 기간에 필요한 페이지를 계산하고, 캐시에 없는 페이지에 대해서만 추가로 요청합니다.

예를 들어 `1개월 → 1년`으로 변경하는 경우:

```text
1개월 선택
→ 1~2페이지 조회 및 캐싱

1년 선택
→ 1~2페이지는 캐시 재사용
→ 3~25페이지만 추가 조회
```

따라서 1년을 선택했다고 해서 기존에 받아온 데이터를 다시 요청하지 않도록 구현합니다.

#### 4. `lastPage`를 기준으로 요청 범위 제한

API 응답에서 전달받은 `lastPage`를 기준으로 실제 요청 가능한 페이지를 제한합니다.

```text
필요 페이지: 25
lastPage: 18

→ 1~18페이지만 요청
```

이를 통해 `lastPage`보다 큰 페이지를 요청하지 않도록 처리합니다.

#### 5. 데이터 조회 완료 후 차트 및 테이블 갱신

추가 페이지를 조회하는 동안에는 로딩 상태를 표시하고, 필요한 데이터 조회가 완료되면 각 페이지의 `DailyPrice` 데이터를 하나로 합칩니다.

```text
페이지 데이터 조회
→ DailyPrice 데이터 병합
→ 날짜 기준 정렬
→ 선택한 기간의 데이터 추출
→ 차트 및 일별 시세 표 갱신
```

예를 들어 1년을 선택하면 25페이지의 데이터를 순차적으로 필요한 만큼 조회하고, 조회가 완료된 데이터를 기준으로 약 245거래일의 캔들 차트와 일별 시세 표를 표시하는 방식으로 구현할 예정입니다.

## 선택 구현 항목

선택 구현 항목 중 다음 기능을 추가로 구현했습니다.

### 관심 화면

#### Pull to refresh

관심 종목 목록을 아래로 당겨 시세를 새로 조회할 수 있도록 구현했습니다.

기존 시세 데이터를 다시 조회하여 최신 가격 정보를 반영하도록 처리했습니다.

### 검색 화면

#### 입력 디바운스 처리

검색어 입력 시 `300ms` 디바운스를 적용했습니다.

사용자가 입력할 때마다 API를 호출하지 않고, 입력이 일정 시간 멈춘 후 검색 요청을 보내도록 처리하여 불필요한 네트워크 요청을 줄였습니다.

#### 토스트 등장 애니메이션

관심 종목 등록 / 해제 시 토스트가 화면 하단에서 위로 올라오는 애니메이션을 적용했습니다.

토스트는 약 2초 동안 노출한 뒤 자동으로 사라지도록 구현했습니다.

## 기술 선택과 이유

### 상태 관리

`Riverpod`을 사용해 관심 종목 상태를 관리했습니다.

관심 종목 데이터는 `SharedPreferences`와 함께 사용하여 앱을 종료했다가 다시 실행해도 관심 종목이 유지되도록 구현했습니다.

반면 검색어, 검색 결과, 정렬 상태 등은 전역 상태로 관리할 필요가 크지 않다고 판단하여 각 화면에서 필요한 범위 내에서 관리했습니다.

### 폴더 구조

Feature 기반 구조로 구성했습니다.

```text
lib/
├── core/
│   ├── network/
│   └── widgets/
├── features/
│   ├── favorite/
│   │   ├── data/
│   │   ├── models/
│   │   ├── presentation/
│   │   └── providers/
│   ├── search/
│   │   ├── data/
│   │   ├── models/
│   │   └── presentation/
│   └── ...
└── theme/
```

기능별로 코드를 묶고, 각 기능 내부에서 `data`, `models`, `presentation`, `providers` 등 역할에 따라 분리했습니다.

이를 통해 특정 기능을 수정하거나 확장할 때 관련 코드를 쉽게 찾을 수 있도록 구성했습니다.

### 주요 패키지

| 패키지               | 사용 목적            |
| -------------------- | -------------------- |
| `flutter_riverpod`   | 관심 종목 상태 관리  |
| `shared_preferences` | 관심 종목 로컬 저장  |
| `dio`                | REST API 통신        |
| `go_router`          | 화면 이동 및 라우팅  |
| `flutter_svg`        | SVG 아이콘 및 이미지 |
| `intl`               | 날짜 및 숫자 포맷    |
| `html`               | API 응답 HTML 파싱   |
| `charset_converter`  | 문자 인코딩 변환     |

### 일별 시세 API

네이버 금융의 일별 시세 API는 JSON이 아닌 HTML을 반환하기 때문에 HTML 파싱을 통해 데이터를 추출했습니다.

또한 응답 HTML의 인코딩이 UTF-8이 아니므로 `ResponseType.bytes`로 응답을 받은 후 `charset_converter`를 사용하여 EUC-KR로 디코딩하도록 구현했습니다.

파싱한 데이터는 `DailyPrice` 모델로 관리하고, 페이지 단위 응답은 `DailyPricePage`로 관리하도록 구성했습니다.

```text
HTML 응답
→ bytes로 수신
→ EUC-KR 디코딩
→ HTML 파싱
→ DailyPrice 생성
→ DailyPricePage 반환
```

### 차트

종목 상세 화면은 구현하지 않았습니다.

구현한다면 별도의 차트 패키지에 의존하기보다 `CustomPainter`를 활용하여 캔들 차트를 직접 그리는 방식을 우선 고려했습니다.

Figma에 맞는 차트 형태와 상승 / 하락 캔들의 색상, 선 등의 표현을 세밀하게 제어할 수 있다는 점을 고려했습니다.

### 디자인 토큰

별도의 디자인 토큰 시스템을 추가하지 않았습니다.

기존 프로젝트에서 제공하는 ThemeExtension 및 디자인 토큰을 활용하여 색상, 크기 등의 스타일을 적용했습니다.

## 직접 판단한 부분과 이유

### 토스트 노출 시간

토스트는 약 2초 동안 노출한 뒤 자동으로 사라지도록 구현했습니다.

관심 종목 등록 / 해제에 대한 단순 피드백이므로 너무 오래 유지할 필요가 없다고 판단했습니다.

또한 새로운 토스트가 표시될 경우 기존 토스트를 먼저 제거하여 여러 토스트가 연속해서 쌓이지 않도록 처리했습니다.

### 로딩 처리

관심 화면에서는 관심 종목 목록을 불러온 뒤 시세를 조회하는 과정에서 각 종목 행에 Skeleton UI를 표시했습니다.

검색 화면에서는 검색 요청 중 `CircularProgressIndicator`를 표시하여 사용자가 요청이 진행 중임을 알 수 있도록 했습니다.

### 네트워크 에러 처리

관심 화면에서 시세 조회에 실패하면 `시세를 불러오지 못했습니다.` 메시지를 표시하도록 처리했습니다.

검색 요청에 실패한 경우에는 검색 결과를 초기화하고 현재 검색 화면에서 결과가 없는 상태로 처리했습니다.

별도의 에러 화면으로 이동시키기보다는 현재 화면의 맥락을 유지하는 방향으로 구현했습니다.

### 긴 종목명 처리

종목명과 `종목코드 · 시장` 정보는 한 줄로 제한하고 `TextOverflow.ellipsis`를 적용했습니다.

화면의 고정된 레이아웃을 유지하면서 긴 종목명으로 인해 가격이나 다른 UI가 밀리는 것을 방지하기 위한 선택입니다.

### 시세가 없는 종목의 정렬

시세 데이터를 아직 받지 못한 종목은 사용자에게 유효한 정렬 값이 없는 상태라고 판단했습니다.

따라서 정렬 시 이러한 종목을 목록의 하단에 배치하는 방향으로 처리했습니다.

### Figma와 다르게 구현한 부분

의도적으로 Figma와 다르게 변경한 부분은 없습니다.

제공된 Figma의 UI와 요구사항을 기준으로 구현했으며, 기능 구현에 필요한 범위에서 Flutter의 기본 동작과 프로젝트에서 제공된 디자인 토큰을 활용했습니다.
